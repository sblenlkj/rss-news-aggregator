## Слайд 2. Архитектура и поток данных

**Небольшое локальное FastAPI-приложение, разделённое по ответственности.**

```text
RSS/Atom → HTTP reader + feedparser → RSS service → SQLite (источники и статьи)
                                               │
                                               └→ GigaChat Embeddings → Qdrant

HTML / JavaScript → FastAPI API → Application services
                                     ├→ UserConfig (фильтры и подписки)
                                     └→ SearchService
                                         ├→ BM25 + pymorphy3 + Navec
                                         └→ GigaChat query embedding + Qdrant
```

- **Domain / value objects:** `ParsedFeed`, `ParsedArticle` для данных парсера; `NewsSource`, `Article`, `User`, `UserConfig`, `KeywordFilter`, `SemanticFilter` для состояния приложения.
- **Application:** сценарии RSS-ingestion и поиска.
- **Ports:** контракты хранилища, RSS-reader, embeddings и векторного индекса.
- **Adapters:** HTTP/feedparser, SQLite/SQLAlchemy, Navec, GigaChat, Qdrant.
- **API/UI:** FastAPI + Swagger; простой HTML/CSS/JS для демонстрации.

**Важно:** RSS источники регистрируются при старте **без скачивания новостей**. Загрузка — вручную или включаемым polling. Разные RSS обновляются асинхронно (до трёх одновременно); таймаут одного не отменяет остальные.

**Что показать:** компактную схему стрелками, не дерево всех файлов.

## Слайд 3. Пользователи и персональные фильтры

**Каждый профиль хранит собственную конфигурацию в SQLite.**

- Создание и выбор нескольких пользователей.
- Для пользователя: набор **ключевых фраз (OR)**, **семантическая тема**, **выбранные RSS-подписки**, опция расширения Navec.
- Конфигурация сохраняется отдельно; при выборе пользователя автоматически загружается.
- В интерфейсе можно изменить поля и сразу запустить поиск **без сохранения**: запрос берёт текущее состояние формы. Кнопка «Сохранить» нужна, чтобы сохранить изменения между сеансами.
- Настройки **выдачи**, а не пользователя: режим поиска, дата получения новости, лимит, порог cosine для Semantic/Hybrid, веса для Hybrid.

**Что показать:** интерфейс выбора профиля и карточку фильтров. На демонстрации можно создать второго пользователя и выбрать другой набор каналов.

## Слайд 4. Поиск по словам: BM25, лемматизация, Navec

**Lexical retrieval:** ищем совпадения в `title + summary + content + tags`.

1. `pymorphy3` приводит русские словоформы к **лемме**: `самолётом → самолёт`. Это **не просто удаление окончаний (stemming)**, а морфологический разбор с выбором нормальной формы.
2. BM25 оценивает документы по **частоте слова в статье (TF)**, **редкости слова в корпусе (IDF)** и **нормализации длины статьи** (параметры `k1=1.5`, `b=0.75`).
3. Опционально Navec расширяет запрос близкими по векторам словами, которые присутствуют в выбранном корпусе. Например, `машина → иномарка` может добавить совпадение. Близость **не гарантирует строгой синонимии**.
4. Keyword-режим сортирует по **сумме BM25 score** сработавших фильтров. Результат объясняет совпавшие и расширенные термины.

**Тезис:** «Пользователь видит не только новость, но и почему она прошла лексический фильтр».

**Что показать:** новость с BM25 score, `matched_terms` и `expanded_terms` при включённом Navec.

## Слайд 5. Семантический и гибридный поиск

**Semantic: GigaChat Embeddings + локальный Qdrant**

- При RSS refresh новые/изменённые статьи сохраняются в SQLite и получают вектора в Qdrant.
- Текст для embedding: **title → tags → summary → content**, первые `NEWS_EMBED_MAX_CHARS=2000` символов. Полный текст остаётся в SQLite и доступен BM25.
- Qdrant хранит векторы по ID статьи; fingerprint позволяет пропускать неизменённые тексты.
- При пользовательском запросе считаем **только эмбеддинг запроса**, ищем сохранённые вектора по cosine similarity; задаём порог сходства.

**Hybrid: Weighted Reciprocal Rank Fusion, а НЕ обученный reranker**

```text
score_RRF(d) =
  Σ_keyword_filters  [w_BM25 / n_keyword / (60 + rank_filter(d))]
+ Σ_semantic_filters [w_semantic / n_semantic / (60 + rank_filter(d))]
```

- `rank` — **позиция новости в ранжированном списке фильтра**, а не её BM25/cosine score.
- По умолчанию в UI веса BM25/Embeddings = **0.4 / 0.6**; сумма = 1.
- Малые величины вроде `0.013115` нормальны для RRF из-за делителя `60 + rank`; это **не вероятность релевантности**.
- Итоговый RRF-score и исходные BM25 / cosine показаны отдельно.

**Что показать:** три режима поиска и новость с двумя сигналами (BM25 и cosine).

## Живая демонстрация после слайда 5 (без отдельного слайда)

**Сценарий, совпадающий с приёмкой преподавателя:**

1. Открываем HTML → показываем предустановленные каналы, при необходимости добавляем новый RSS через «Добавить RSS».
2. Выбираем/создаём пользователя → выбираем RSS-подписки и фильтры.
3. Запускаем **Keyword**, затем **Semantic**, затем **Hybrid**; обращаем внимание на объяснение каждого результата и итоговый score.
4. Публикуем новую тестовую статью в **собственный RSS**.
5. Нажимаем «Обновить» у тестового RSS → повторяем поиск → показываем, что статья появилась в ленте.
6. При необходимости меняем фильтр прямо в форме без сохранения, подтверждаем изменение выдачи.

**Итог:** выполнены ключевой, семантический и многопользовательский уровни; данные хранятся локально, поиск объясним, новый RSS можно подключить из интерфейса.

**Важная оговорка докладчика:** внешний RSS может временно не отвечать; для гарантированной демонстрации используем локальный тестовый RSS. Сервис показывает ошибку источника, но сохраняет ранее загруженные новости.

**После пятого слайда:** переключаемся в работающую HTML-страницу, не тратим время на Swagger, если преподаватель не попросит.

## Шпаргалка для вопросов преподавателя (не отдельный слайд)

- **Почему два хранилища?** SQLite — структурированные статьи, пользователи и фильтры; Qdrant — вектора для семантического similarity search.
- **Индексируем ли каждый раз заново?** Нет. При refresh индексируем только новые/изменённые статьи; при поиске эмбеддинг нужен только для запроса. Для ранее загруженных статей есть ручной `POST /api/v1/search/index`.
- **Зачем BM25, если есть embeddings?** BM25 лучше контролирует точные слова и объяснение; embeddings находят тематически близкие тексты; гибрид объединяет оба.
- **Чем лемматизация отличается от stemming?** Лемматизация использует морфологический анализ и нормальную форму слова, stemming механически сокращает слово.
- **Почему RRF-score малый?** Это сумма обратных рангов с константой 60, не raw cosine и не вероятность.
- **Откуда берутся данные?** RSS/Atom XML, а не scraping HTML полного текста статьи.
- **Почему тестовый RSS не появляется в SQLite сразу?** Он сначала публикуется в XML, потом проходит тот же ingestion, что и внешний RSS.
- **Как проверяем соответствие требованиям?** План в `docs/rss-test-scenarios.md`; фактическая демонстрация через HTML.
