## 1. RSS: что мы получаем и где ищем

RSS/Atom — XML-ленты публикаций. Наш парсер использует feedparser и приводит разные форматы к общей записи статьи.

| Поле | Откуда берётся / смысл | В поиске? |
| --- | --- | --- |
| title | Заголовок RSS item / Atom entry | Да, оба движка |
| summary | Краткое описание; может отсутствовать | Да, оба движка |
| content | RSS content:encoded либо Atom content; может отсутствовать | Да, оба движка |
| tags | Категории / теги статьи | Да, оба движка |
| url | Ссылка на исходную публикацию | Нет, для перехода |
| external_id | GUID / идентификатор записи | Нет, для идентификации |
| published_at | Дата публикации, если предоставлена | Не текстовый признак; показывается в карточке |
| fetched_at | Время получения нашим агрегатором | Не текстовый признак; **по нему** действует фильтр «Добавлено с даты» |

Парсер извлекает текст из HTML-фрагментов RSS, убирая разметку. Важно: **мы не скачиваем полный HTML текст новости с её сайта**. Поэтому если RSS содержит только заголовок и теги, summary и content останутся пустыми.

Для BM25 **одна статья — один объединённый документ**. Порядок непустых блоков: title → summary → content → tags. Это один поток токенов, в котором **нет специальных коэффициентов для title или tags**. Если слово встречается в разных полях, все его появления участвуют в общей частоте TF.

Для embeddings порядок другой: **title → tags → summary → content**, затем берём максимум первые **2000 символов** (настраиваемый NEWS_EMBED_MAX_CHARS). Такой порядок отдаёт приоритет коротким информативным полям до обрезания длинного content. Полный текст остаётся в SQLite и используется BM25 без этой обрезки.

Поиск сначала ограничивается **RSS-подписками выбранного пользователя**; при указанной дате дополнительно фильтруется по fetched_at. Полученные статьи образуют корпус, по которому рассчитывается лексическая статистика.

### Один пример статьи

- title: «Машины с автопилотом появились в городе»
- summary: «Новая технология управления транспортом»
- content: «На испытаниях машина несколько раз ... Машиной управлял алгоритм ...»
- tags: «транспорт», «автомобили»

Поиск по «машина» сможет обнаружить слово и в заголовке, и в content; «автомобили» — другое нормализованное слово, но Navec потенциально может связать его с «машина».

## 2. Лемматизация: зачем pymorphy3

Русские слова склоняются и спрягаются: **машина, машины, машиной, машинах**. Сравнение только строк не позволило бы считать их одной формой слова.

Наш нормализатор:

1. Разбивает строки на Unicode-токены (слова и числа), приводит к нижнему регистру.
2. Для кириллических русских слов использует **pymorphy3**, выбирает первый предложенный морфологический разбор и его normal_form.
3. Для других языков и чисел сохраняет нижний регистр.
4. Применяет одинаковую процедуру **к документам и к запросу**.

Условно: «самолётом» → «самолёт», «машины» → «машина» (в соответствующем грамматическом смысле).

**Лемматизация не равна stemming.** Stemmer обычно отсекает окончания по правилам, иногда получая несуществующую основу. Морфологический анализатор старается вернуть словарную лемму, например для глагола инфинитив. При омонимии первый разбор может ошибаться: контекстную неоднозначность наше простое решение не устраняет.

**Стоп-слова отдельно не удаляются.** Распространённые слова обычно получают низкий IDF в BM25, но токены остаются в статистике длины и частот.

## 3. BM25: основная формула поиска по словам

BM25 отвечает: насколько данная статья соответствует **словам запроса**, если учесть повторения слов, редкость в корпусе и длину документа.

### 3.1. Обозначения

- N — число статей **текущего выбранного корпуса**.
- tf(t,d) — сколько раз нормализованное слово t встретилось в статье d **по всем полям вместе**.
- df(t) — в скольких разных статьях встретилось слово t хотя бы один раз.
- |d| — длина статьи в нормализованных токенах.
- avgdl — средняя длина статьи в токенах по корпусу.
- k1 = **1.5**, b = **0.75** — параметры именно нашей реализации.

### 3.2. Точная формула

$$
\operatorname{BM25}(d,q)
=\sum_{t\in q\cap d}\operatorname{IDF}(t)
\frac{\operatorname{tf}(t,d)(k_1+1)}
{\operatorname{tf}(t,d)+k_1\left(1-b+b\frac{|d|}{\operatorname{avgdl}}\right)}
$$

где:

$$
\operatorname{IDF}(t)
=\ln\left(1+\frac{N-\operatorname{df}(t)+0.5}{\operatorname{df}(t)+0.5}\right).
$$

Суммирование идёт по уникальным нормализованным терминам запроса, которые встретились в статье. Повторение слова в самой поисковой фразе наш код предварительно устраняет; повторения **в статье** сохраняются и учитываются.

**Смысл трёх частей:**

- **IDF — редкость слова.** Если термин присутствует лишь в немногих статьях корпуса, он информативнее и весит больше. Слово «новость» почти в каждой статье — менее информативно.
- **TF — количество появлений.** Два появления обычно лучше одного, но пять не дают пятикратный вклад: формула имеет **насыщение TF**.
- **Нормализация длины.** В длинной статье слово чаще встречается случайно. При сопоставимой TF более короткий документ обычно имеет преимущество.

### 3.3. Если слово повторяется в заголовке, тегах, summary и content

Предположим:

| Место | Лемма «машина» |
| --- | ---: |
| title | 1 |
| summary | 1 |
| content | 3 |
| tags | 0 |
| **TF всего** | **5** |

Мы **не вычисляем четыре отдельных BM25-score**. Получаем один tf(машина,d) = 5, а длина документа учитывает токены всех четырёх полей.

Если пользователь искал фразу «машина самолёт», то BM25 рассчитывает отдельный вклад для каждой из двух лемм и складывает их.

Важно: **слово в заголовке само по себе не получает бонуса**. Если title короткий, общий документ тоже может оказаться коротким, и это косвенно влияет через нормализацию длины, но специального boost(title) нет.

### 3.4. Числовой пример (искусственный, не данные твоего RSS)

Пусть N = 100 статей, слово «машина» встречается в df = 5 статьях. Тогда:

$$
\operatorname{IDF}(\text{машина})
=\ln\left(1+\frac{100-5+0.5}{5+0.5}\right)
\approx 2.91.
$$

При длине статьи, равной средней, нормирующее слагаемое равно k1 = 1.5.

- tf = 1 → TF-множитель равен 1 → вклад около **2.91**.
- tf = 3 → TF-множитель равен 3·2.5/(3+1.5) ≈ **1.667** → вклад около **4.85**.

То есть повторения повышают score, но **не линейно**.

BM25 score может быть 5, 7, 10 и больше. Это **не вероятность**, не процент и не cosine. Значение **6.791** на твоём скриншоте само по себе не выглядит аномальным: редкое слово с высоким IDF может дать большой вклад даже при единственном совпадении.

### 3.5. Несколько ключевых фильтров

На HTML-странице **одна строка = отдельный OR-фильтр**. Например:

    машина
    самолёт

Статья попадает в выдачу, если удовлетворяет хотя бы одному фильтру. В режиме Keyword окончательная оценка — сумма BM25-score по сработавшим фильтрам:

$$
S_\text{keyword}(d)=\sum_{f:\,d\text{ найден по }f}\operatorname{BM25}_f(d).
$$

Пример: по «машина» статья набрала 3.1, по «самолёт» 2.2 → итог 5.3. Если совпала только с одним фильтром на 6.8, её итог — 6.8; значит, она выше. Выдача сортируется по убыванию **итоговой** метрики, затем применяется лимит.

При разных пользовательских подписках меняется корпус → меняются N, df и avgdl → **та же статья может получить другой BM25-score**.

**Особенность реализации:** для учебного небольшого корпуса BM25 статистика рассчитывается заново на текущем наборе статей при поиске. Это не то же самое, что сохранённый Qdrant-векторный индекс.

## 4. Navec: поиск похожих слов

BM25 с лемматизацией умеет отождествлять «машина» и «машиной», но **не умеет сам отождествлять «машина» и «иномарка»** — это разные леммы.

Navec хранит предобученные вектора **слов**. Похожие по употреблению слова иногда близки в векторном пространстве. Мы сравниваем их по cosine:

$$
\cos(x,y)=\frac{x\cdot y}{\|x\|\|y\|}.
$$

### Как Navec работает именно у нас

1. Запрос «машины» нормализуется до «машина».
2. Берутся **уникальные леммы, встречающиеся в выбранных RSS-статьях**.
3. Из них остаются те, для которых Navec знает вектора.
4. Сравниваем вектор «машина» со словарными векторами этих лемм.
5. Оставляем похожие слова с cosine **не ниже 0.55**, максимум **5** добавлений на поисковый фильтр.
6. Передаём BM25 исходное слово **и** найденные дополнения.

Например, если в корпусе есть подходящие слова:

    машина → [автомобиль, иномарка]

BM25 теперь может сработать по «иномарка», даже если буквального слова «машина» в статье нет. **Оригинальный фильтр пользователя при этом не переписывается**.

**Почему предпросмотр Navec отличается от результатов поиска?** Предпросмотр берёт похожие слова из первых **50 000 частотных слов модели**, независимо от RSS. Фактическое расширение берёт близкие слова **только из текущего корпуса**. Отсюда ситуация на твоём экране: в предпросмотре «автомобиль», а в найденной статье — «иномарка».

**Нюанс ранжирования:** наш код **не ослабляет вес добавленных слов**. «Иномарка» получает такой же обычный BM25-вклад TF/IDF, как «машина». Поэтому статья, найденная только по Navec-расширению, иногда может стоять выше статьи с исходным термином — если расширенное слово редкое в корпусе. Это не техническая ошибка, а свойство текущей стратегии расширения.

Navec — не строгий словарь синонимов: возможны тематически близкие, но не взаимозаменяемые слова. Поэтому опция включается/выключается пользователем.

## 5. Семантический поиск: GigaChat Embeddings и Qdrant

### 5.1. Что такое embedding

Embedding — численный вектор, представляющий текст. Обученная модель старается расположить близкие по смыслу тексты близко в пространстве векторов.

Например, запрос «автономный летательный аппарат обходит препятствия» **может** оказаться близок к статье «беспилотный самолёт с нейросетевым автопилотом», даже без точных совпадений лемм. Это зависит от модели; семантическое совпадение не гарантировано.

### 5.2. Когда создаётся вектор статьи

При обновлении RSS для новых или изменённых статей мы готовим текст в порядке:

    title → tags → summary → content → обрезка до 2000 символов

Текст превращается в embedding через **GigaChat Embeddings**, затем сохраняется в **Qdrant** вместе с ID статьи, source ID, названием модели и fingerprint подготовленного текста.

Fingerprint позволяет не отправлять неизменённые статьи повторно. Если поменялись модель или индексируемая часть текста, вектор нужно обновить. Если GigaChat недоступен, статья всё равно остаётся в SQLite, а её embedding может потребовать повторной индексации.

2000 — лимит **символов**, а не токенов GigaChat. У длинного content часть после лимита не участвует в embedding; BM25 продолжает видеть полный RSS-текст.

### 5.3. Что происходит при поиске

1. Берём семантический запрос пользователя (например, «беспилотный летательный аппарат»).
2. **Вычисляем embedding только этого запроса** через GigaChat.
3. В Qdrant ищем похожие уже сохранённые векторы, ограничивая поиск статьями выбранных RSS.
4. Ранжируем по cosine similarity.
5. Применяем порог, например **0.5**. Статьи ниже порога не проходят этот фильтр.

$$
\cos(q,d)=\frac{q\cdot d}{\|q\|\|d\|}.
$$

Cosine для обычных ненулевых векторов находится между −1 и 1. **0.8 — не «80% вероятности релевантности»**, а сходство направлений двух векторов. Чем выше значение, тем ближе вектора при данном представлении.

Для единственного семантического фильтра итоговый score в режиме Semantic — его cosine. Если тем несколько, наш SearchService суммирует cosine-score сработавших semantic-фильтров.

**Ключевое отличие от BM25:** при каждом семантическом поиске **не индексируем все статьи заново**. Вектора статей сохраняются в Qdrant, а embedding нового запроса вычисляется каждый раз.

## 6. Зачем Hybrid и что делает Weighted RRF

BM25 и cosine работают в **разных численных шкалах**. BM25 может дать 6.791, а cosine — 0.840. Складывать их напрямую некорректно: большая величина BM25 может доминировать лишь из-за шкалы, а не из-за лучшей релевантности.

Поэтому мы объединяем **ранги** двух выдач через Reciprocal Rank Fusion.

### 6.1. С одним фильтром каждого типа

$$
S_\text{RRF}(d)
=\frac{w_B}{60+r_B(d)}+\frac{w_S}{60+r_S(d)}.
$$

Здесь:

- r_B(d) — место статьи в BM25-рейтинге, **начиная с 1**;
- r_S(d) — место в семантическом рейтинге, **начиная с 1**;
- w_B и w_S — веса; в интерфейсе обычно **0.4 и 0.6**, сумма = 1;
- 60 — константа сглаживания;
- если статьи нет в конкретном списке, вклад этого списка **0**.

**Пример, не реальный результат с твоего экрана:** статья первая по BM25 и третья по Semantic.

$$
S_\text{RRF}
=\frac{0.4}{61}+\frac{0.6}{63}
\approx0.006557+0.009524
=\boxed{0.016081}.
$$

Вот почему Hybrid показывает **0.013115** или **0.016** — это нормальный масштаб суммы обратных рангов. Это **не вероятность**, не проценты, не сумма исходных scores.

### 6.2. Если фильтров много

В нашем поиске каждая keyword-строка и каждая semantic-тема образуют **собственный ранжированный список**. Для гибрида вес каждого движка делится на число его активных фильтров:

$$
S_\text{hybrid}(d)
=\sum_{f\in K:\,d\in f}\frac{w_B/|K|}{60+r_f(d)}
+\sum_{g\in S:\,d\in g}\frac{w_S/|S|}{60+r_g(d)}.
$$

K — набор активных keyword-фильтров, S — semantic-фильтров. При отсутствии документа в каком-либо списке слагаемого нет. Нормализация мешает десяти keyword-фильтрам автоматически «перевесить» единственную семантическую тему только из-за их числа.

Сами пороги cosine применяются **до RRF**, то есть документ с cosine ниже порога не участвует в семантическом ранжировании.

**RRF — не обученный нейронный reranker.** Это детерминированная процедура слияния ранжированных списков.

### 6.3. Какая метрика сортирует в каждом режиме

| Режим | Итоговый ranking_score |
| --- | --- |
| Keyword | Сумма BM25 по сработавшим keyword-фильтрам |
| Semantic | Сумма cosine по сработавшим semantic-фильтрам |
| Hybrid | Взвешенный RRF по рангам фильтров |

Выдача всегда сортируется **по убыванию итогового ranking_score**, после чего берётся нужное число статей. В карточке видны также оценки отдельных фильтров — поэтому можно объяснить, за что статья получила место.

**Не сравнивать абсолютные числа между режимами:** BM25 6.8, cosine 0.84 и RRF 0.013 измеряют разные вещи.

## 7. Полный мысленный пример: ищем «машина»

Корпус состоит из трёх условных статей:

- **A:** «Иномарка попала в ДТП». Слова «машина» нет, зато есть «иномарка».
- **B:** «Машины с автопилотом». «Машина» встречается несколько раз.
- **C:** «Новая система автономного движения». Буквального слова «машина» нет, смысл близок автономному транспорту.

**Keyword без Navec:** B находится благодаря лемматизации «машины» → «машина». A и C могут не попасть в выдачу.

**Keyword с Navec:** если вектор «иномарка» достаточно близок и это слово есть в корпусе, A тоже может попасть в выдачу. Её BM25-score определяется TF, IDF и длиной; это не обязательно ниже прямого совпадения B.

**Semantic с темой «автономный транспорт»:** модель может поставить B и C выше A, если их векторы ближе к смыслу темы, даже без слова «машина».

**Hybrid:** получаются списки с ранговыми позициями; RRF суммирует вклады рангов, учитывая установленные веса. Статья, хорошо ранжирующаяся в обеих ветках, часто выигрывает, но конкретный порядок зависит от корпуса, весов и threshold.

**Если завтра добавить другие RSS:** даже без изменения текста статьи BM25-score может измениться, поскольку изменились N, df и средняя длина. При Semantic неизменённые вектора статей сохранятся; изменится только набор доступных для поиска статей.

## 8. Частые вопросы преподавателя

**Слово встретилось три раза в content и один раз в title — что будет?** Общий tf=4. Веса полей у нас одинаковые, отдельного title boost нет.

**Почему значение BM25 выше 1?** Это TF/IDF-оценка, не вероятность и не нормализованный cosine.

**Почему pymorphy3 — не «библиотека удаления окончаний»?** Она выполняет морфологический анализ и возвращает лемму.

**Почему Navec в предпросмотре не показал «иномарка», но в поиске она есть?** Разные множества кандидатов: словарь 50 тысяч слов против слов из выбранного корпуса.

**Откуда статья без точного слова?** Navec-расширение в Keyword либо смысловая близость embeddings в Semantic/Hybrid.

**Почему не векторизуем весь корпус на каждый поиск?** Векторы статей хранятся в Qdrant и меняются только при индексации новых/изменённых статей. При запросе считаем только embedding вопроса.

**Почему RRF-score такой маленький?** Делитель 60+ранг; итог порядка 0.01 ожидаем.

**Что если RSS не содержит content?** Ищем по доступным title/summary/tags, не подменяем content текстом сторонней страницы.

## 9. Самая короткая формулировка

**BM25** ищет совпадающие слова, учитывает их повторения, редкость в текущем корпусе и длину статьи. **pymorphy3** нормализует разные словоформы к леммам. **Navec** опционально добавляет близкие по вектору слова из текущих статей. **GigaChat Embeddings** превращает текст в смысловой вектор, а **Qdrant** хранит векторы и ищет их через cosine. **Weighted RRF** объединяет ранги BM25 и Semantic без сложения несопоставимых исходных метрик.
