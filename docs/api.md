# HTTP API — RSS News Aggregator

Актуально на 22.11.2026. Источники: `src/news_aggregator/api/routes.py`, `api/schemas.py` и `main.py`.

Сервер: `uv run uvicorn news_aggregator.main:app --reload --port 8000`.
Интерактивная документация: http://127.0.0.1:8000/docs.
API-префикс: **`/api/v1`** (кроме HTML и XML endpoints).

## Системные endpoints

| Метод | Путь | Что возвращает |
| --- | --- | --- |
| GET | `/` | Одностраничный HTML-интерфейс |
| GET | `/static/*` | CSS/JavaScript |
| GET | `/docs` | Swagger UI (FastAPI) |
| GET | `/api/v1/capabilities` | `keyword`, `synonyms_enabled`, `semantic_enabled`, `semantic_model`, `hybrid_method` |

`/capabilities` показывает **настроенные** движки, а не результат реального теста соединения с GigaChat.

## Автоматическая инициализация RSS при запуске

В `application/rss/bootstrap.py` перечислены четыре внешних русскоязычных канала. При старте FastAPI выполняется idempotent bootstrap: добавить отсутствующие каналы, добавить собственный `/test-feed/rss.xml`, без автоматического обновления новостей. Существующие UUID и пользовательские подписки не сбрасываются; отключённые каналы не включаются повторно. При startup bootstrap нет сетевых запросов: ошибки внешних каналов появляются только после ручного или периодического обновления и записываются в `last_error`.

Локальный тестовый RSS при старте только регистрируется. После запуска ручное обновление использует тот же HTTP-reader, что и внешние каналы.

`NEWS_POLL_INTERVAL_SECONDS=0` выключает периодический polling. Startup bootstrap работает независимо, но лишь регистрирует источники; HTTP-запросов при старте нет. Положительный интервал включает фоновое обновление. Ручное обновление доступно через `/sources/refresh`.

## RSS-источники

| Метод | Endpoint | Запрос | Результат |
| --- | --- | --- | --- |
| GET | `/api/v1/sources` | — | Список `SourceRead` |
| POST | `/api/v1/sources` | `{"url":"https://example.org/rss"}` | Создаёт RSS в SQLite, сразу пытается обновить, возвращает `SourceRead` (201) |
| GET | `/api/v1/sources/{source_id}/status` | UUID | Статус последней проверки: `last_checked_at`, `last_success_at`, `last_error` |
| POST | `/api/v1/sources/{source_id}/refresh` | UUID | Загружает XML, сохраняет статьи, возвращает `source_id`, `fetched`, `upserted` |
| POST | `/api/v1/sources/refresh` | — | Обновляет все активные источники; возвращает `{"successful": [...], "failed": [...]}` и статус HTTP 200 даже при частичных ошибках |
| DELETE | `/api/v1/sources/{source_id}` | UUID | Деактивирует источник, **не удаляет его статьи** (204) |

`SourceRead`: `id`, `feed_url`, `title`, `is_active`, timestamps проверки/успеха и `last_error`.

Особенность: если новое RSS не удалось скачать, источник остаётся зарегистрированным, ошибка видна в `last_error`. Если polling включён, он повторит попытку в следующем цикле; при `NEWS_POLL_INTERVAL_SECONDS=0` обновление выполняется только вручную. `refresh_all_report` возвращает **и успешные, и неуспешные** обновления. Каждый элемент `successful` содержит `source_id`, `fetched`, `upserted`; каждый элемент `failed` — `source_id`, `error`. При частичном успехе HTTP 200 означает, что операция выполнена, а не что все RSS доступны. Одиночный `POST /sources/{id}/refresh` при сетевой ошибке возвращает 502, а `SourceRead.last_error` сохраняет причину (`ConnectTimeout`, если у исключения нет текста). HTTP-reader выполняет одну повторную попытку для `ConnectTimeout`/`ReadTimeout` и не повторяет запросы при HTTP 4xx.

## Новости

| Метод | Endpoint | Что делает |
| --- | --- | --- |
| GET | `/api/v1/articles` | Все сохранённые статьи |
| GET | `/api/v1/articles?source_id=<UUID>` | Статьи конкретного RSS |

`ArticleRead` содержит: `id`, `source_id`, `title`, `url`, `external_id`, `summary`, `content`, `tags`, `published_at`, `fetched_at`. `summary` и `content` независимы и необязательны. Поисковый текст собирается из `title + summary + content + tags`.

## Пользователи и персональная конфигурация

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| GET | `/api/v1/users` | Список пользователей |
| POST | `/api/v1/users` | Создать пользователя: `{"name":"Alice"}`; возвращает id и дату (201) |
| GET | `/api/v1/users/{user_id}` | Получить пользователя |
| GET | `/api/v1/users/{user_id}/config` | Получить подписки и фильтры |
| PUT | `/api/v1/users/{user_id}/config` | **Полностью заменить** подписки и фильтры пользователя |

Пример конфигурации пользователя:

```json
{
  "source_ids": ["00000000-0000-0000-0000-000000000001"],
  "filters": [
    {"type": "keyword", "value": "нейросеть", "enabled": true},
    {"type": "semantic", "value": "новые языковые модели", "threshold": 0.5, "enabled": true}
  ],
  "add_synonyms": true
}
```

`add_synonyms` сохраняется **в настройках пользователя** и включает Navec при keyword/hybrid поиске. Слова расширяются динамически по статьям выбранных RSS, без изменения исходных фраз.

Схемы фильтров содержат UUID `id` (если не передан, генерируется новый). Поле `type` — `keyword` или `semantic`; `enabled=false` отключает правило. `PUT /config` — замена всего набора, не частичное добавление.

## Поиск

**`POST /api/v1/search`** принимает конфигурацию в теле запроса (можно ещё не сохранять её пользователю), а также режим и параметры выдачи:

```json
{
  "source_ids": ["00000000-0000-0000-0000-000000000001"],
  "filters": [
    {"type": "keyword", "value": "нейросеть", "enabled": true},
    {"type": "semantic", "value": "исследования ИИ", "threshold": 0.5, "enabled": true}
  ],
  "add_synonyms": true,
  "mode": "hybrid",
  "bm25_weight": 0.4,
  "semantic_weight": 0.6,
  "date_from": "2026-11-01",
  "limit": 20,
  "offset": 0
}
```

Замените UUID на **реальный** `source_id` из `GET /sources`.

| Параметр | Значение |
| --- | --- |
| `mode=keyword` | BM25 с pymorphy3; `add_synonyms=true` добавляет слова, подобранные Navec при наличии весов |
| `mode=semantic` | GigaChat embedding + Qdrant cosine; без подключения embedding-провайдера — HTTP 501 |
| `mode=hybrid` | Совмещает ранги BM25 и cosine через **weighted RRF**, не обученный cross-encoder |
| `bm25_weight`, `semantic_weight` | При Hybrid веса в диапазоне 0–1 с суммой 1, по умолчанию 0.5/0.5; задают вклад каждого ранжированного сигнала, а не масштаб исходного score |
| `semantic_threshold` | Применяется только к Semantic/Hybrid: минимальное cosine сходство, по умолчанию 0.5 (legacy-пороги фильтров сохраняют совместимость) |
| `date_from` | Нижняя граница по дате **добавления** `Article.fetched_at` (включительно), не по дате публикации |
| `limit`, `offset` | Пагинация: limit 1–100 (по умолчанию 20), offset от 0 |

Пример структуры ответа:

```json
{
  "items": [
    {
      "article": {"id": "...", "title": "...", "source_id": "...", "summary": "...", "content": "..."},
      "ranking_score": 1.23,
      "ranking_method": "bm25",
      "matches": [
        {
          "filter_id": "...",
          "filter_type": "keyword",
          "engine": "bm25",
          "score": 1.23,
          "matched_terms": ["нейросеть"],
          "expanded_terms": [],
          "threshold": null,
          "model": null
        }
      ]
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

В реальном ответе `article` содержит также остальные поля `ArticleRead`. Для semantic матчей `engine=cosine`, `score` — cosine similarity, присутствуют `threshold` и `model`. Для нескольких фильтров статья может иметь несколько причин совпадения. Выдача отсортирована по итоговой метрике, не по одной из оценок отдельных фильтров. `ranking_score` — **итоговый score сортировки**, `ranking_method` указывает метрику: сумма BM25 для Keyword, сумма cosine для Semantic, weighted RRF для Hybrid. Результаты сортируются по убыванию `ranking_score`; `matches[].score` — оценка отдельного фильтра и может отличаться от итоговой.

### Ручная индексация Qdrant

**`POST /api/v1/search/index`** — ручная одноразовая синхронизация Qdrant с уже сохранёнными SQLite-статьями; тело запроса не требуется. Ответ `{"checked": N, "message": "Vector index synchronized"}`. `checked` — количество проверенных статей, **не число вызовов embedding API**: неизменённые векторы пропускаются по fingerprint. Если индекс не сконфигурирован — 501, если SDK/API недоступен — 502. При семантическом поиске векторы статей больше не создаются автоматически; при пустом Qdrant будут нулевые результаты до backfill/refresh.

### Предпросмотр Navec

`POST /api/v1/search/expand` возвращает похожие слова по эмбеддингам Navec **без RSS, пользователя и сохранённых статей**:

```json
{"keywords": ["трансформер", "нейросеть"]}
```

Ответ, например: `{"suggestions": {"трансформер": ["..."], "нейросеть": ["..."]}}`. Предложения зависят от модели и не гарантированно являются синонимами. Для экономии ресурсов предпросмотр ищет по 50 тысячам наиболее частотных слов Navec; вычисление матрицы проводится лениво при первом обращении. Порог 0.55 и максимум 5 предложений.

При **самом поиске** BM25 расширяет ключевые слова только словами, реально присутствующими в выбранных RSS-статьях, поэтому предпросмотр и поисковое расширение могут различаться. Исходные фильтры не перезаписываются. Если Navec не подключён, ответ 501.

### Что изменилось в HTML

До выбора/создания пользователя настройки фильтров и секция поиска скрыты. При выборе профиль загружается автоматически; ручная кнопка загрузки не требуется. Секция «Пользователь и фильтры»: keyword и semantic фразы, подписки, сохраняемая галочка Navec и кнопка предпросмотра. Секция «Настроить выдачу»: `mode`, `date_from`, `limit` (1–100); поле `semantic_threshold` показывается только для Semantic/Hybrid, веса `bm25_weight` и `semantic_weight` — только для Hybrid. Параметры выдачи не сохраняются в профиль. Для существующих старых `SemanticFilter.threshold` совместимость сохранена: при отсутствии нового параметра используется сохранённый порог или 0.5.

После `POST /test-feed/articles` форма показывает подтверждение публикации; в SQLite запись появится после RSS refresh.

## Собственный тестовый RSS

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| POST | `/api/v1/test-feed/articles` | Опубликовать запись в тестовый RSS (201) |
| GET | `/test-feed/rss.xml` | Получить валидный RSS XML для последующего обычного ingestion |

```json
{
  "title": "Новая модель поиска",
  "summary": "Краткое описание",
  "content": "Полный текст новости в RSS",
  "tags": ["NLP", "AI"]
}
```

Тестовые посты сохраняются отдельно в JSON тестового publisher. **Публикация напрямую не создаёт статью в основной SQLite**. Тестовый источник уже регистрируется при старте. После публикации достаточно выполнить refresh этого источника (или дождаться следующего цикла polling, если он включён). После этого новость появится через `GET /articles` и в `POST /search`.

## Приёмочный smoke-test

1. Запустить локально `uv run uvicorn news_aggregator.main:app --reload --port 8000`.
2. Открыть `/` и `/docs`, проверить `GET /api/v1/capabilities`.
3. Создать RSS и пользователя, затем указать выбранные `source_ids` в конфигурации.
4. Опубликовать собственную тестовую статью с характерным ключевым словом в поле `content`.
5. Обновить тестовый RSS. Проверить `GET /articles`.
6. Запустить keyword, semantic и hybrid search и сравнить объяснения.
7. Перезапустить FastAPI, убедиться, что SQLite-данные остались.

## Ограничения

- Внешний GigaChat и RSS могут быть временно недоступны из-за сети, TLS или ограничений API; для воспроизводимой демонстрации тестируйте локальный RSS.
- Открытый публичный API нельзя разворачивать без защиты RSS-fetch от SSRF. Для локального учебного сценария это открытый технический долг.
- `GET /articles` пока возвращает весь список без пагинации; `POST /search` имеет пагинацию.
